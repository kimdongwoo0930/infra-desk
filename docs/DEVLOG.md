## 2026-10-27 · 디자인 v2 3단계: 컨테이너 탭 (표 위 · 로그 아래)

브랜치 `design-v2/containers`. 컨테이너 표와 로그를 한 탭으로 합쳤다. 서버에 보내는 명령(시작·정지·재시작, 로그 읽기, SSH 접속 방식)은 바꾸지 않았다.

**한 일**
- **`LogLine`(ssh 패키지):** `docker logs --timestamps`의 줄을 시각·수준(정보/경고/오류)·내용으로 해석한다. 수준은 **추측**이다(단어 `error/fatal/panic/exception/traceback`, `level=error`, HTTP 5xx → 오류; `warn`, `level=warn`, HTTP 4xx → 경고). 틀릴 수 있다는 점을 클래스 설명에 적었다.
- **네트워크 열:** `docker stats`가 이미 주던 `NetIO`를 `Container.netIo`로 읽는다(서버에 보내는 명령은 그대로).
- **`ContainerLogView`(로그 패널):** 컨테이너 전환 칩(상태 점), 전체/경고/오류 + 개수, 검색, 줄 수(200/1000/5000), 줄바꿈, 새로고침, 하단의 실제 명령과 "보이는 줄 / 받은 줄 · 경고 · 오류". 서버에 접속하지 않고 `onReload`로 요청만 한다. `LogTable`은 줄 선택·복사가 되도록 표로 만들었다(복사하면 화면에 보이는 글자가 나온다).
- **`ContainersPanel`(표) 새 모양:** 칩(전체/실행 중/멈춤)과 검색, CPU 막대, 네트워크 열, 멈춘 컨테이너는 노란 "멈춤 (0) · 3일 전", 행 끝에 작업 아이콘(셸·DB 콘솔·재시작·정지, 멈춘 행은 ▷ 시작 하나). 로그 아이콘과 "시작" 글자는 사용자 요청으로 뺐다: 행을 클릭하면 로그가 뜨니 아이콘이 필요 없고, 시작도 삼각형 아이콘만 둔다. 아이콘 위치 계산은 `ContainerRowActions`, 글자 변환은 `ContainerFormat`으로 떼어 테스트했다.
- **`ContainersTab`:** 위 표 / 아래 로그를 `JSplitPane`으로 나눈다. 손잡이를 표 높이에 자동으로 맞추고, 사용자가 끌면 그 뒤로는 건드리지 않는다.
- **연결(`ServerScreen`, `MainFrame`):** 컨테이너 탭을 열었다. 표는 개요 탭 본문에서 이 탭으로 옮겼다(개요에는 7단계에서 컨테이너 요약이 돌아온다). 탭 이름 옆에 개수 배지를 붙인다. 표의 행을 클릭하면 그 컨테이너의 로그가 아래에 뜨고, 반대로 로그의 칩을 고르면 표의 행이 강조된다.
- **로그 별도 창(`ContainerLogWindow`):** 사용자 요청으로, 컨테이너 하나의 텍스트만 보여 주던 예전 `ContainerLogsDialog`를 지우고 **로그 화면 전체**를 새 창에 하나 더 연다. 창마다 `ContainerLogView`를 따로 가져서 선택과 거르기가 독립이다. 창을 연 순간의 목록으로 시작하고 이후 목록 변화는 따라가지 않는다. 창을 닫으면 그 창의 타이머를 멈춘다.

**결정과 이유**
- **"따라가기"를 "자동 새로고침"으로 바꿨다(사용자 의견).** 처음에는 시안의 "따라가기"를 새로 읽을 때 맨 아래로 스크롤하는 것으로 만들었는데, 새 줄을 가져오지 않는 버튼이라 이름과 기대가 어긋났다. 켜 두면 10초마다 조용히(불러오는 중 화면 없이) 다시 읽는다. 안전장치: 기본 꺼짐, 실행 중인 컨테이너에서만, 패널이 화면에 보일 때만, 읽는 중이면 건너뜀, **읽기에 실패하면 스스로 꺼짐**(틀린 키로 10초마다 접속을 시도하지 않게), 맨 아래를 보고 있던 경우에만 새 줄을 따라 내려감. 실제 `docker logs -f` 스트리밍은 SSH 채널을 계속 열어 두어야 해서 접속 규칙을 정한 뒤에 한다. PRD의 "조회 주기" 표에 적었다.
- **컨테이너 탭을 열 때만 로그를 읽는다.** 서버를 고를 때마다 로그를 읽으면 불필요한 SSH 조회가 생긴다. 탭이 닫혀 있으면 목록만 읽고, 탭을 열면 첫 컨테이너를 자동으로 고른다(`ServerScreen`이 맡고 테스트로 고정).
- **표 위 문구에 "30초마다"를 적지 않았다.** 시안에는 있지만 사실이 아니다: 컨테이너 목록은 주기적으로 읽지 않고, 서버를 고를 때(30초 캐시)·서버 상태가 바뀔 때·새로고침이나 동작 뒤에 읽는다. 그래서 `docker ps · 10:48:01 기준`만 적는다. (처음 PRD에 "30초마다"로 잘못 적었다가 코드를 확인하고 바로잡았다.)
- **나눈 위치 저장, 로그 패널 접기(⌄), 실시간 스트리밍은 하지 않았다.** 저장은 설정 저장소가 필요하고, 접기는 시안 기능이지만 이번 범위에서 뺐다.

**겪은 문제(같은 실수 두 번)**
- 가짜 컨테이너 id를 `문자열.repeat(n).substring(0, 64)`로 만들다가 짧은 이름에서 길이가 모자라 두 번 실패했다(갤러리 스냅샷, `ServerScreenTest`). 항상 64자가 되도록 고정 자릿수(`%08x`)나 0으로 채우는 방식으로 고쳤다.
- 백그라운드로 돌린 명령의 오류가 보이지 않아, `UiSnapshot` 수정이 조용히 실패한 것을 한 번 늦게 알았다. 이후 파일 존재와 로그를 먼저 확인한다.

**확인:** 컨테이너 쪽 테스트가 새로 50여 개(LogLine 11, 로그 패널 26, 표 12, 글자 변환 6, 작업 아이콘 위치 계산 7, 서버 화면 6 등), 전체 통과. 스냅샷으로 컨테이너 탭과 로그 별도 창을 확인했다. 눌러 봐야 아는 것은 `USER_TEST_LIST.md`에 올렸다.

**남은 일:** 4단계 모니터링 탭(차트를 개요에서 옮김) → 5 파일 → 6 터미널 → 7 개요 탭. 로그 실시간 스트리밍은 접속 규칙(`SessionPool`) 논의 뒤에.

## 2026-10-27 · 디자인 v2 2-c: 서버 화면 틀(머리 + 탭 줄 + 상태 막대)을 화면에 붙임

2단계 "공통 틀"의 마지막 조각. 2-a/2-b에서 만든 `TabBar`, `StatusBar`를 처음으로 실제 화면에 붙였다. 기능은 그대로이고 배치만 바뀌었다.

- **`ServerDetailPanel`을 둘로 나눔:** 예전에는 머리(이름, 배지, 버튼)와 본문(정보 격자, 차트, 컨테이너)이 한 패널이고 통째로 스크롤됐다. 탭이 생기면 머리는 고정, 본문만 바뀌어야 해서 머리를 `ServerHeader`로 떼어 냈고, `ServerDetailPanel`은 "개요 탭 본문"만 남았다. 둘을 묶는 `ServerScreen`(머리 + `TabBar` + 스크롤 본문)을 새로 만들었다.
- **`MainFrame` 변경은 최소로:** `detail`의 타입만 `ServerDetailPanel`에서 `ServerScreen`으로 바꿨다. `ServerScreen`이 `onSsh`, `onAction`, `setBusy`, `showActionError`, `show`, `setFacts`, `setFactsMessage`, `metrics()`, `containers()`를 같은 이름으로 머리와 본문에 넘겨 주어서 `MainFrame`의 호출부는 그대로다. 본문 스크롤 래퍼(`JScrollPane`)는 `ServerScreen` 안으로 옮겼다.
- **`ServerHeader`로 옮긴 것:** 시작/정지/재부팅/SSH 버튼의 상태별 활성화 규칙, 요청 중 표시, 직접 연결 기기의 전원 버튼 숨김, 부제(계정·리전·shape)와 IP 가림 연동(IP 가림을 켜고 끌 때 부제의 IP도 같이 바뀐다). 로직은 그대로 옮겼고 `ServerHeaderTest` 6개로 동작을 고정했다.
- **`ServerScreen.show()`는 머리를 먼저 채운다:** 직접 연결 기기의 주소를 IP 가림 대상으로 등록하는 일이 머리의 `show()`에 있고, 개요 본문이 그 뒤에 주소를 표시하기 때문이다. 순서가 바뀌면 주소가 가려지지 않는다.
- **탭:** 개요만 동작한다. 모니터링·컨테이너·파일·터미널은 3~7단계에서 하나씩 열 때까지 `ComingSoon`(비활성 + "준비 중" 글자), 로그는 시안처럼 처음부터 준비 중이다. 기존 "SSH 열기" 버튼과 터미널 흐름은 그대로 동작한다.
- **상태 막대:** `MainFrame`이 서버 화면과 터미널 화면 모두에 보이도록 루트 맨 아래에 붙였다. 항목은 "SSH 연결 —"(준비 중), "실시간 꺼짐/켜짐 · 서버", 오른쪽에 "상태 30초 · 메트릭 1분마다"와 "v버전". 조회 주기 문구는 `RefreshPolicy.NORMAL_INTERVAL`과 새 상수 `METRICS_INTERVAL`(메트릭 타이머도 같은 값을 쓴다)에서 만들어서 주기를 바꾸면 문구가 따라 바뀐다. 실시간 표시는 `LiveHooks.showToggle` 한 곳에서 갱신한다.
- **준비 중으로 둔 것(`// 준비 중(v2):` 주석):** 즐겨찾기 별(저장소 없음), [⋯] 버튼(메뉴 내용 미정), 탭 5개, 상태 막대의 SSH 연결 수(`SessionPool`이 열린 연결을 읽어 주는 방법이 없다 — GAPS.md "먼저 상의" 5번). 별은 즐겨찾기가 켜진 것처럼 보이지 않도록 윤곽선 아이콘(`star.svg`)으로 했고, `more.svg`(⋯)와 함께 새로 추가했다.
- **일부러 안 한 것:** 시안 상태 막대의 "전송 1개 진행 중 · 63%"는 전송 대기열이 SFTP 창 안에 있어서 파일 탭(5단계)에서 함께 한다. 시안 머리의 "확인 필요" 배지와 부제의 "2 OCPU · 12 GB"는 개요 탭(7단계)에서 한다. 타이틀바(빠른 실행 입력칸, 요약, 읽기 전용 스위치)와 사이드바 위쪽([개요][활동 기록])도 개요 화면(9단계)과 함께 한다.
- **시안과 다른 점:** 개요 탭 안(정보 격자, 차트, 컨테이너 표)은 7단계에서 시안대로 바꾸므로 지금은 예전 모습 그대로다. 탭 5개가 모두 "준비 중"이라 시안(로그만 준비 중)보다 산만하다. 3~7단계에서 하나씩 열면 시안과 같아진다.
- 확인: 전체 테스트 313개 통과, 스냅샷 성공(머리·탭 줄·상태 막대가 시안과 같은 위치에 나온다). 눌러 봐야 아는 것(툴팁, 스크롤, 크기 조절, 실시간 표시)은 `USER_TEST_LIST.md`에 올렸다.
- **남은 일:** 3단계 컨테이너 탭(표 위 · 로그 아래) → 4 모니터링 → 5 파일 → 6 터미널 → 7 개요 탭. 탭을 열 때 `ServerScreen`의 `setComingSoon` 호출을 지우고 본문 카드를 추가한다.

## 2026-10-27 · 디자인 v2 2-a/2-b: 탭 줄과 상태 막대 (아직 화면에 안 붙임)

2단계 "공통 틀"(서버 화면 머리 + 탭 구조 + 상태 막대)을 세 조각으로 나눴다. 이번에는 기존 화면에 영향이 없는 새 부품 둘만 만들었다. 화면에 붙이는 2-c(`ServerHeader`, `ServerScreen`, `ServerDetailPanel`/`MainFrame` 수정)는 확인받고 한다.

- **`TabBar`(2-a):** 밑줄 탭 줄. 탭 안쪽 여백 위아래 9·좌우 12, 글자 13, 선택은 굵은 글자 + 2px `ACCENT_LINE` 밑줄, 줄 맨 아래에 1px `DIVIDER`. 탭마다 문자열 `id`("overview" 등)를 줘서 화면 코드가 번호가 아니라 id로 말하게 했다. `setCount(id, n)`은 옆에 개수 배지, `setComingSoon(id)`는 눌리지 않고 "준비 중" 글자와 안내가 붙는다. 선택이 바뀔 때만 리스너를 부른다. 굵은 글자 기준으로 폭을 잡아 선택이 바뀌어도 옆 탭이 밀리지 않는다.
- **`StatusBar`(2-b):** 아래 26px 막대. 위쪽 1px 구분선, `PANEL_BG`, 글자 11.5 흐린 색. 어떤 항목을 보여 줄지는 모른다: `addLeft/addRight(글자)`가 돌려주는 라벨의 `setText`로 나중에 바꾼다. SSH 연결 수처럼 읽을 방법이 없는 항목은 라벨에 `ComingSoon`을 씌워 자리만 둔다.
- **버그 하나(테스트가 잡음):** `TabBar` 안쪽 클래스 `Tab`은 `JToggleButton`을 상속하는데, AWT의 `ImageObserver`가 `HEIGHT`(= 2)라는 상수를 물려준다. 상속받은 이름이 바깥 클래스의 `HEIGHT`보다 우선해서, 컴파일 오류 없이 탭 높이가 2가 됐다. 상수 이름을 `TAB_HEIGHT`로 바꿔 피했고 이유를 주석에 남겼다. Swing 컴포넌트를 상속하는 클래스 안에서는 `HEIGHT`, `WIDTH`, `X`, `Y`처럼 AWT가 쓰는 이름을 상수로 짓지 않는다.
- 테스트: `TabBarTest` 7개(선택·알림·준비 중 탭이 눌리지 않음·밑줄 픽셀·폭), `StatusBarTest` 3개. 전체 307개 통과. `ComponentGallery`에 두 부품을 추가했다.
- **남은 일(2-c):** 서버 화면 머리(`ServerHeader`: 별·이름·배지·부제·버튼) + `ServerScreen`(머리 + `TabBar` + 본문) + `StatusBar`를 `MainFrame`에 붙인다. 탭은 개요만 동작하고 모니터링·컨테이너·파일·터미널은 3~7단계에서 하나씩 열 때까지 `ComingSoon`, 로그는 처음부터 준비 중이다. SSH 연결 수는 `SessionPool`이 열린 연결을 읽어 주는 방법을 먼저 정해야 해서 준비 중으로 둔다.

## 2026-10-23 · 창이 안 보이면 CPU만, 다시 보이면 바로 갱신

사용자 제안: 창이 숨어 있을 때 사이드바·트레이에 필요한 건 CPU뿐이니 CPU만 읽자. 창이 다시 올라오면 5분 캐시를 기다리지 말고 바로 조회하자.

- **CPU만 측정:** 창이 안 보이면(X로 메뉴 막대에만 있거나 Dock 최소화) 직접 연결 서버는 1분마다 `ProcStats.CPU_ONLY`만 실행한다. Linux는 `/proc/stat` 두 줄을 1초 간격으로, macOS는 `iostat` 1초 측정이다(이 맥에서 실제로 실행해 `@cpu 21` 출력을 확인). 메모리·네트워크는 읽지 않으므로 그 시간대 차트는 비어 있다(`Sample.cpuOnly`는 나머지 값이 NaN, `metrics()`가 메모리·네트워크 시리즈에서 뺀다). 사용자가 이 빈 구간을 감수하기로 했다.
- **창이 다시 보일 때(`componentShown`, `windowDeiconified`):** 서버 상태 목록(사용자 요청이 아닌 조용한 재조회), 사이드바 CPU, 직접 연결 서버의 전체 샘플, 선택한 서버의 차트를 바로 읽는다. 창을 연달아 여닫아도 쌓이지 않도록 10초 안의 반복은 건너뛴다. `SamplingGate`의 "멈춤"은 풀지 않는다(자동 접속 제한 취지 유지). 서버 상세 정보(5분)와 컨테이너(30초)는 기존 캐시 기간을 따른다.
- "보이지 않음"의 기준은 창 상태다. 듀얼 모니터에서 다른 앱을 쓰느라 포커스가 없거나 다른 창에 가려진 것은 보이는 것으로 보고 전체 측정을 계속한다.
- 그 전에 최소화 상태에서는 `isShowing()`만 보고 분기해서 트레이가 없으면 측정이 건너뛰어질 수 있었는데, 숨김 상태(`windowHidden()`)를 기준으로 바꿨다.
- **직접 확인하지 못한 것:** 창 복원 때 즉시 갱신되는 동작과 숨은 동안 CPU만 재는 동작은 화면 이벤트(`MainFrame`)라 자동 테스트가 없다. `USER_TEST_LIST.md`에 넣었다. 파싱과 차트 시리즈 처리는 `SshMetricsServiceTest`가 검증한다.

## 2026-10-23 · 창이 안 보일 때도 측정은 1분마다

SSH 접속 풀을 만들기 전에는 샘플 하나가 새 접속·인증이라 서버 로그에 기록이 쌓여서, 창이 숨으면 5분에 한 번만 측정하게 했다(`SamplingGate`). 풀 이후에는 조회(QUERY) 연결이 숨어 있어도 유지돼서 1분마다 하는 측정이 **열린 연결에 채널만 여는 것**이다. 5분은 사이드바·트레이 CPU가 너무 오래된 값이 된다는 판단으로 되돌렸다.

- **버그 수정:** 풀의 "숨음" 처리가 X로 닫을 때만 켜지고 Dock 최소화에는 연결돼 있지 않았다. 최소화(`windowIconified`/`windowDeiconified`)에도 연결했다. 그래서 최소화 중에도 조회 연결만 남는다.
- **중복 제거:** 실시간 모드(2초)로 직접 연결 서버를 읽는 중에도 1분 측정이 같이 돌아서, 결과가 화면에 반영되지 않는데 서버에서 명령이 한 번 더 실행됐다. 실시간 모드 중에는 그 서버의 1분 측정을 건너뛴다.
- 서버 상태 조회(30초)는 숨어 있어도 그대로 둔다(메뉴 막대 상태 표시를 최신으로 유지).
- **직접 확인하지 못한 것:** "실시간 모드 중 1분 측정을 건너뜀"은 화면 코드(`MainFrame`)라 자동 테스트가 없다. 창 최소화/복원 때 풀이 정리되는 것도 화면 이벤트라 `USER_TEST_LIST.md`에 있다.

## 2026-10-23 · SFTP 업로드가 권한을 지키도록 수정

SFTP 안전장치 중 "권한 보존"을 먼저 했다. 코드를 읽고 "덮어쓰면 권한이 사라질 것 같다"고 말했던 것을 **임시 조사용 테스트로 먼저 확인**했다(저장소에는 남기지 않음). 확인 결과: 덮어쓰면 `secret.env` 600 → 644, `run.sh` 755 → 644가 됐다. 비밀 파일이 다른 사용자에게 읽히게 바뀌는 보안 문제이고, 앱의 `편집` 저장도 같은 경로라 똑같이 영향받았다.

**정한 것 (사용자 결정)**
| 항목 | 결정 |
|---|---|
| 덮어쓰기 | 기존 서버 파일의 권한을 **확인하고 그 뒤에** 그대로 유지 |
| 새 파일 | 내 컴퓨터 파일의 권한을 따름 (Windows는 서버 기본값) |
| 소유자가 달라질 때 | 전송 하나가 끝나면 경고를 **한 번만** |

**구현** (`TransferQueue.uploadFile`, 자세한 규칙은 [ssh.md](architecture/ssh.md))
- 덮어쓰기 전에 `stat`으로 기존 권한·소유자를 읽는다. 임시 파일은 **내용을 올리기 전에** 비운 채로 만들어 `chmod`부터 한다. 이름을 바꾼 뒤 다시 읽어 확인하고, 다르면 실패로 알린다.
- 권한을 맞추지 못하면 내용을 올리지 않고 실패한다(원본은 그대로). 서버가 권한을 안 알려주면 건드리지 않는다(`chmod 000` 방지).
- 새 폴더는 내 컴퓨터 폴더의 권한을 받되, 안에 파일을 다 올린 뒤에 적용한다(읽기 전용 폴더에도 올릴 수 있게).
- `RemoteFile`에 소유자 번호(`uid`)를 추가했고, MINA 속성의 `Perms`/`UidGid` 플래그가 있을 때만 값으로 인정한다. 소유자가 바뀐 파일은 `Job.ownerChangedNames()`로 모아 `SftpDialog`가 전송당 한 번 경고한다.

**테스트** (`UploadPermissionTest`, 실제 MINA 서버 + 서버의 이상 동작은 `RemoteFiles`를 감싸서 흉내)
덮어쓰기 600/755/660 유지, 새 파일이 내 컴퓨터 권한(600/755/644)을 따름, **임시 파일이 내용을 쓰기 전에 이미 600이고 비어 있음**, 새 폴더의 권한(비공개 700, 읽기 전용 포함)과 적용 시점, 소유자 변경 경고(같은 소유자면 없음, 폴더는 모아서 한 번), 서버가 권한을 안 알려줄 때 `chmod`가 없음, `chmod`가 거부되면 실패하고 원본이 그대로, 최종 권한이 확인되지 않으면 실패.

## 2026-10-23 · SSH 접속 풀

명령마다 새로 접속·인증하던 구조를 바꿨다. 접속은 서버의 인증 로그에 남고 시간도 걸린다. 앞서 한 `SamplingGate`는 접속을 시도하는 횟수를 줄였을 뿐 접속을 재사용하지는 않았다. 노션 「아이디어」의 "SSH 세션 풀"을 이야기로 정한 대로 구현했다. 규칙의 상세는 [ssh.md](architecture/ssh.md#접속-풀-sessionpool).

**정한 것 (사용자 결정)**
| 항목 | 결정 | 이유 |
|---|---|---|
| 풀의 단위 | 서버·목적별 **연결(TCP+인증) 하나**, 그 위에 채널. 목적 4개(QUERY / COMMAND / FILES / TRANSFER) | 큰 전송이 같은 연결의 조회를 느리게 만들지 않게. 서버 로그에는 연결을 맺을 때만 남는다 |
| 터미널 탭 | 풀 밖. 사용할 때 열고 닫음 | 사용자가 직접 여닫는 연결이라 풀의 수명 규칙과 맞지 않는다 |
| 실시간 모드 | QUERY 연결의 채널 | |
| 창이 메뉴 막대로 숨음 | 조회 연결만 남김. 쓰지 않는 다른 연결은 바로, 쓰는 연결은 끝난 뒤 닫음 | 전송 중에 창을 닫아도 전송이 끊기지 않게 |
| 재시도 | **조회만 한 번.** COMMAND는 하지 않음 | 응답만 못 받았을 뿐 서버에서 이미 실행됐을 수 있어서, 재시도하면 명령이 두 번 실행될 수 있다 |
| 12시간 수명 | 쓰는 곳이 없는 빈틈에 교체. QUERY는 빈틈이 10분 동안 안 생기면 강제 | 한 키로 인증된 연결을 너무 오래 두지 않으려는 보안 목적. 강제 교체는 QUERY만 한다(전송·명령을 끊지 않는다) |
| 설정 변경·서버 삭제 | 그 서버의 연결을 즉시 끊음 | 키나 사용자 이름을 바꿨는데 옛 연결이 12시간 남으면 바꾼 의미가 없다 |
| 접속 횟수 카운터 | 코드에 넣지 않음 | 나중에 서버 로그로 직접 센다. 접속 수 검증은 테스트에서 서버 쪽 세션 수로 한다 |

**구현**
- `Purpose`, `SessionPool`(새로 만듦), `MinaShellConnector`가 풀을 쓴다. `ShellSession.close()`와 `RemoteFiles.close()`가 **채널만 닫고 연결은 풀에 돌려준다**(이전에는 연결째 닫았다).
- `ShellConnector`에 목적을 받는 `exec`/`sftp`와 `setBackground`, `invalidate`를 `default`로 추가해서 데모 접속기와 기존 테스트의 가짜는 바꾸지 않았다. 목적을 밝히지 않은 `exec`는 COMMAND로 취급한다.
- 호출 지점에서 목적을 밝힌다: 측정·서버 정보·컨테이너 목록·로그·실시간 = QUERY, 일괄 실행·컨테이너 시작·정지 = COMMAND, SFTP 탐색 = FILES, 전송 대기열 = TRANSFER(`openTransferFiles`).
- `TerminalService`가 SSH 설정 저장·삭제 때 연결을 끊고, `MainFrame`이 창이 숨고 나타날 때(`componentHidden`/`componentShown`)를 풀에 알린다.
- 풀은 개인키를 보관하지 않고 바뀌었는지 알아볼 해시만 쓴다.

**테스트로 발견한 것 (heartbeat가 처음에는 동작하지 않았다)**
- 30초 heartbeat로 끊어진 연결을 감지하려고 인증 뒤에, 그다음 인증 전에 세션에 MINA 속성을 설정했는데 둘 다 **효과가 없었다.** 컴파일도 되고 겉보기에는 정상이라 테스트(응답을 버리는 중계기로 연결을 조용히 끊는 시험)가 없었다면 몰랐을 문제다.
- 원인은 MINA의 `ClientConnectionService`가 heartbeat 설정을 **세션 생성자에서 한 번만** 읽어 `final` 필드에 둔다는 것(소스 확인). 연결을 받은 시점에는 이미 늦다.
- 그래서 **풀 연결용 `SshClient`를 따로 두고 그 클라이언트에 heartbeat를 설정**했다. 터미널용 클라이언트는 그대로다. 대신 클라이언트가 둘이라 NIO 자원이 조금 더 든다(메모리는 측정하지 않았다).
- 음성 대조도 했다. 응답 없음 감지(`HEARTBEAT_NO_REPLY_MAX`)를 끄면 이 테스트가 **실패한다.** 테스트가 우연히 통과하는 게 아님을 확인했다.
- `HEARTBEAT_REPLY_WAIT`는 2.13.0부터 deprecated라서 쓰지 않았다.

**확인**
- 실제 MINA 서버를 프로세스 안에 띄워 **서버가 본 접속 수**를 센 테스트 18개(`SessionPoolTest`): 명령 30번에 접속 1번, 목적별 연결 4개와 채널을 닫아도 연결 유지, 터미널은 풀 밖, 연결이 끊기면 조회만 한 번 다시 맺음, 인증 실패는 다시 접속하지 않음, 키가 바뀌면 새 연결과 옛 연결 종료, 설정 변경 시 즉시 끊김, 창이 숨으면 조회만 남고 쓰는 연결은 끝난 뒤 닫힘, 12시간 수명(빈틈 교체, 조회 강제는 10분 뒤, 전송은 강제하지 않음), 유휴 종료, 끊어진 연결 감지.
- 전체 테스트 251개 통과(1개는 기존 Windows 전용 테스트가 macOS에서 건너뜀). 스냅샷 정상.

**직접 확인하지 못한 것**
- **실제 서버에서 접속이 줄었는지.** 서버 로그의 접속 기록 수는 재 보지 못했다(맥미니에서 `log show --predicate 'process == "sshd"'`로 세면 된다).
- 노트북이 잠자기에서 깨어난 뒤의 동작. 끊어진 연결은 heartbeat로 감지하지만, 여러 서버가 한꺼번에 재접속하는 것을 시차를 두어 분산하지는 않았다(조회는 `SamplingGate`의 대기 규칙을 따른다).
- 클라이언트가 둘이 된 것의 메모리 영향.
- Windows에서의 동작.
- 화면에서 X로 닫았다가 다시 열 때 연결이 실제로 정리되는지(창 이벤트 연결은 코드로만 확인했다).

## 2026-10-23 · SFTP 내려받기 기본 위치를 Downloads로

Windows에서 서버 파일을 더블클릭해 내려받으면 `Downloads`가 아니라 사용자 루트(`C:\Users\이름`)에 쌓인다는 제보. 원인은 내려받기가 "왼쪽 내 컴퓨터 패널의 현재 폴더"로 저장되는데, 그 패널이 항상 홈 폴더에서 시작하기 때문이다.

- 왼쪽 패널의 시작 위치를 `~/Downloads`로 바꿨다. 그 폴더가 없으면 홈 폴더(`LocalFiles.startFolder`). macOS와 Windows 모두 폴더 이름이 `Downloads`다.
- **내려받기 위치를 패널과 분리(사용자 요청):** 위 수정만으로는 왼쪽 패널을 다른 폴더로 옮기면 거기로 받아서 여전히 헷갈린다. 서버 파일 더블클릭·`내 컴퓨터로 다운로드` 버튼·우클릭 메뉴는 패널이 어느 폴더에 있든 **다운로드 폴더**(`LocalFiles.home()`, 시작 폴더와 같음)로 받는다. **끌어서 놓기**만 놓은 곳(패널 현재 폴더 또는 폴더 행)으로 받는다. 같은 이름 확인도 패널 목록이 아니라 받을 폴더를 직접 본다.
- **내 컴퓨터 파일 편집 버튼:** 왼쪽 패널에 `편집` 버튼과 우클릭 메뉴 항목을 추가했다. 서버와 주고받을 것이 없어서 서버 편집처럼 임시 복사본을 만들지 않고 그 파일 자체를 편집기로 연다(`ExternalEditor`).
- 노션 「SFTP 안전장치」의 "더블클릭 = 편집" 항목은 하지 않았다. 사용자가 더블클릭은 다운로드로 두기로 했다.
- **전송 패널 닫기(사용자 요청):** 전송이 끝난 뒤에도 아래 패널이 계속 남아 있었다. 지우기로 목록을 다 비워도 패널이 접히지 않는 버그가 원인이었다(접는 판단이 작업 상태가 바뀔 때만 있었다). 이제 지우기 뒤에도 접힌다. `끝난 항목 모두 지우기`는 완료뿐 아니라 실패·취소한 항목도 지운다(실패 항목을 지우면 이어받기용 임시 파일도 함께 지워진다). 오른쪽 위 X는 패널만 접는다(목록과 진행 중인 전송은 그대로). 접은 뒤에는 아래 상태줄의 `전송 목록 보기 (n)` 버튼으로 다시 연다. 새 전송이 시작되거나 실패가 생기면 저절로 다시 나타나서 실패를 놓치지 않는다.
- **버그 수정: 겹치는 파일을 덮어쓰며 받으면 전송 패널이 안 나타남(사용자 제보).** 바로 위 "다시 나타남" 판단이 새 작업인지를 작업 상태가 QUEUED인지로 봤는데, 이 판단은 EDT가 알림을 처리하는 시점의 상태를 읽는다. 작은 파일은 그때 이미 끝나 있어서 패널을 닫아 둔 상태에서는 다시 나타나지 않았다. 스냅샷에서 "X로 닫음 → 겹치는 이름을 덮어쓰며 받기"를 먼저 재현해 실패를 확인한 뒤 고쳤다. 이제 새 작업인지는 그 작업의 첫 알림인지(`announced`)로 판단한다.
- **직접 확인하지 못한 것:** 실제 Windows에서 시작 폴더가 `Downloads`로 뜨는지(폴더 이름 판별만 테스트). 윈도우에서 다운로드 폴더를 다른 드라이브로 옮긴 경우(재지정된 "알려진 폴더")는 따라가지 않고 홈 아래 `Downloads`만 본다.

## 2026-10-20 · 직접 연결 서버에 자동으로 SSH 접속하는 횟수 제한

SSH 접속은 서버의 인증 로그에 남고, 인증 실패가 반복되면 서버의 보안 도구가 이쪽 IP를 차단할 수 있다. 서버 쪽 로그가 도배되거나 서버에 부담이 가면 안 된다는 요청으로 SSH 접속 구조를 코드로 전수 조사했다.

**조사 결과 (직접 연결 서버 기준. 클라우드 서버는 OCI API를 쓰므로 해당 없음)**
- 분당 측정이 **1분마다, 창이 숨어 있어도 계속** 새 SSH 접속을 맺는다(하루 1,440번/서버). 접속을 재사용하지 않는다.
- 측정이 실패해도 **물러서지 않고** 1분마다(서버 목록을 읽을 때마다 30초 경로까지) 다시 시도한다. 키가 틀린 채 두면 10분에 20번쯤 인증 실패가 쌓인다.
- 상태 확인용 TCP 접속이 30초마다 있다(하루 2,880번/서버).
- 이미 괜찮은 것: 터미널 자동 재접속 없음, 실시간 모드는 사용자가 켤 때만(10분 뒤 꺼짐, 서버 쪽 반복 명령에도 상한), 명령이 가볍고 타임아웃·출력 상한이 있음, 응답 없는 서버나 믿지 않은 호스트 키에는 백그라운드로 접속하지 않고 절대 묻지 않음.

**고친 것:** `service/SamplingGate`(새로 만듦)가 자동 접속을 제한한다. 규칙은 [service.md](architecture/service.md#자동-ssh-접속-규칙-samplinggate).
- 설정 문제(호스트 키, 키 파일)는 첫 실패에, 인증 실패는 연속 2번째에 **자동 접속을 멈춘다**. 이유가 화면에 나오고 설정 저장·새로고침·서버 정보 읽기 성공 때 다시 시도한다.
- 그 밖의 실패는 2분 → 5분 → 15분으로 길게 기다린다.
- 창이 숨어 있거나 최소화되면 서버당 5분에 한 번, 어떤 경우든 15초 안에 두 번 접속하지 않는다.
- `ExecResult`에 실패 종류(`failureKind`)를 추가해서 "다시 시도해도 소용없는 실패"를 구분한다.
- 가짜 접속기로 접속 횟수를 세는 테스트: 인증 실패 후 100분 동안 접속 0번, 60번 요청해도 연결 실패는 6번 이하, 창이 숨으면 30분에 6번 등.

**안 한 것(당시 `TODO.md`에 적었다. 이후 `TODO.md`는 삭제했고 세션 풀은 노션 「아이디어」에서 다룬다):** 상태 확인 TCP 간격 늘리기, 서버당 SSH 연결 하나를 유지하는 구조(근본 해결), `docker stats`를 필요할 때만 실행.

**직접 확인하지 못한 것:** 서버 로그에 실제로 몇 줄이 쌓이는지, fail2ban의 실제 차단 조건, macOS 서버에서 접속 하나의 비용, TCP 확인 접속이 sshd 로그에 남는지.

## 2026-09-29 · 버전 자동 증가

- **버전 규칙** (사용자 결정): 앱 버전은 빌드(run 번호)에서 자동 계산. `n = run - 0`(빌드 번호 그대로)일 때 `1.(n÷10).(n%10)` → 빌드 16 → 1.1.6, 20 → 1.2.0. 메이저(1→2)는 사용자가 대규모 패치 후 직접 올림 (`build.gradle.kts`의 `majorVersion`, `runOffset` 수정).
- 이유: 버전은 1.0.0 고정, 빌드 번호만 올라가서 번호가 두 개라 헷갈렸음. 파일 이름·앱 정보·릴리스 제목에 실제 버전이 드러남.
- 업데이트 비교와 `beta-N` 태그는 그대로 빌드 번호 사용 (이미 설치된 앱 호환). 릴리스 제목은 "InfraDesk 1.1.0 Beta (빌드 N)" — `(빌드 N)`은 업데이트 확인이 파싱하므로 유지.
- 오프셋 0은 `build.yml`(릴리스 제목용)과 `build.gradle.kts` 두 곳에 있으니 같이 고칠 것. `-PappVersion`은 여전히 우선.
- 남은 일: 실제 CI에서 다음 빌드(16)가 1.1.6으로 나오는지 확인.

## 2026-09-29 · 연결이 잠깐 끊겨도 서버 목록 유지

인터넷이 잠깐 끊기면 그 계정의 서버가 사이드바에서 사라지고 에러만 남았다.

- **원인:** 조회가 실패하면 그 계정의 서버 목록을 빈 목록으로 덮어썼다. 재시도는 원래 계속 돌고 있어서 연결이 돌아오면 복구됐지만, 그 사이 화면이 비었다.
- **수정:** 실패한 계정은 마지막으로 받은 서버 목록을 유지하고 에러 줄만 덧붙인다(`MainFrame.keepLastKnownServers`). 다음 폴링이 성공하면 에러 줄이 사라지고 새 상태로 바뀐다.
- **폴링 간격:** 45초 → 30초. 계정당 폴링 1회에 OCI 호출 3번이라 분당 6회 수준이라 제한과 거리가 멀다. 실패해도 같은 간격으로 계속 재시도한다(백오프 없음).
- **새로고침이 먹통이던 문제:** 연결이 끊긴 뒤 새로고침 버튼도 자동 폴링도 반응이 없어 앱을 재시작해야 했다. OCI 클라이언트에 타임아웃이 없어 요청이 멈추면 `refreshing`이 계속 true로 남았고, 그동안 모든 새로고침이 무시됐다(추정 원인, 재현은 못 함). 수정: OCI 클라이언트에 연결 5초·읽기 20초 타임아웃, 수동 새로고침은 진행 중인 요청이 있어도 새로 시작하고 이전 요청의 늦은 결과는 버린다(`reloadGeneration`).
- **끊긴 동안 표시:** 유지한 서버는 마지막 상태(실행 중 등)를 그대로 보여주지 않고 `UNREACHABLE`("응답 없음", 회색 점, CPU 숨김)로 바꿔 보여준다. 직접 연결 서버가 끊겼을 때와 같은 표시이고, 시작/정지/재부팅 버튼도 비활성화된다. 알림은 실패한 계정을 건너뛰므로 "서버가 멈췄어요" 오알림은 없다.

## 2026-09-28 · Windows 업데이트가 적용되지 않던 문제

Windows 사용자 보고: 업데이트를 받고, 앱이 꺼졌다 켜지지만 계속 빌드 10으로 켜졌다.

- **원인(추정, 로그 확인 대기):** 교체 스크립트(PowerShell)가 앱의 현재 폴더를 물려받았다. 탐색기에서 더블클릭해 실행하면 현재 폴더가 앱 폴더라, 스크립트가 **앱 폴더 안에서** 돌았다. Windows는 어떤 프로세스의 현재 폴더인 폴더의 이름을 바꾸지 못하게 한다. 그래서 `Move-Item`이 20초 동안 실패하다 "update skipped"로 끝났고, 기존 앱을 다시 켰다. macOS는 이런 잠금이 없어서 성공했다. CI 테스트는 JVM의 현재 폴더가 프로젝트 폴더라서 이 상황을 재현하지 못했다.
- **수정:**
  - 스크립트는 작업 폴더(`%LOCALAPPDATA%\InfraDesk\cache\update`)에서 시작한다(`ProcessBuilder.directory`). 스크립트 안에서도 먼저 임시 폴더로 이동한다.
  - 재시작한 앱은 앱 폴더를 작업 폴더로 해서 띄운다.
  - 이름 바꾸기에 실패하면 마지막 오류 메시지를 `update.log`에 남긴다.
  - 교체에 실패한 채 기존 버전이 다시 켜지면, 앱이 시작할 때 "업데이트를 적용하지 못했어요" 알림을 한 번 띄운다(`recentSwapFailure`, 10분 안의 실패만 해당). 아무 일도 없었던 것처럼 보이지 않게 하기 위해서다.
- **실제 환경:** 2026-09-29, Windows에 빌드 12를 직접 설치하고 트레이에서 빌드 13으로 업데이트했다. 받기 → 점검 → 교체 → 재시작 후 빌드 13으로 켜졌다. 이제 macOS(7 → 8)와 Windows(12 → 13) 모두 앱 안 업데이트가 확인됐다.
- **주의:** 교체 스크립트는 **지금 실행 중인(옛) 앱**에 들어 있다. 그래서 빌드 10·11에서 업데이트하면 같은 이유로 또 실패한다. 이 수정이 들어간 빌드는 한 번 직접 받아 설치해야 하고, 그다음 업데이트부터 앱 안에서 적용된다.

## 2026-09-28 · 직접 연결 서버 3단계: 주소 가리기 · SSH 모니터링

사용자 피드백을 반영했다. 첫째, 추가한 서버의 IP가 가려지지 않았다. 둘째, CPU·메모리 정보를 볼 수 없었다. 모니터링은 SSH로만 가져오는 게 맞다는 의견이었다.

### 주소 가리기
- **원인:** 원래 공인 IPv4만 가리고 사설 IP(192.168.x, Tailscale 100.x)와 호스트 이름은 보여 줬다. 게다가 부제의 `주소:포트` 줄은 가림 처리를 거치지 않았다.
- **수정:** 직접 연결 서버의 주소는 `IpPrivacy.protect`로 등록한다. 종류와 관계없이 IP는 `•••.•••.•••.20`, 호스트 이름은 `m•••••`로 가린다. 목록을 불러올 때 등록하므로 상세 화면, 부제, 터미널 상태 줄, 오류 문구에 모두 적용된다. 눈 아이콘으로 드러낼 수 있다. 긴 이름부터 바꿔서 `mac-mini.tail….ts.net`이 부분만 가려지지 않게 했다.

### SSH 모니터링 (1분마다)
- **`SshMetricsService`:** 앱이 켜져 있는 동안 1분마다, 실행 중이고 SSH가 설정된 직접 연결 서버에 짧은 명령 하나(`ProcStats.ONE_SHOT`: 1초 간격 스냅샷 2개, Linux와 macOS 모두)를 보낸다. 최근 1시간을 메모리에 모아 둔다.
- **화면:** 상세 그래프("SSH로 1분마다 수집 · 앱이 켜져 있는 동안의 기록"), 사이드바 CPU %, 트레이가 클라우드 서버와 똑같이 동작한다. 실시간 모드(2초)는 그대로 따로 켤 수 있다.
- **호스트 키:** 백그라운드 수집은 호스트 키를 묻지 않는다(모르는 키면 실패). 그래서 처음 수집은 서버 정보 읽기(필요하면 키를 확인하는 창을 띄움)가 성공한 뒤에 시작한다.
- **부하:** 서버당 1분에 SSH 연결 한 번, 약 1~2초. 클라우드 서버에는 SSH 수집을 하지 않는다(OCI Monitoring 사용).
- **CPU / 메모리 칸:** 서버 정보 읽기에 `@cpus`(`nproc` 또는 `hw.ncpu`)와 `@memkb`(MemTotal 또는 `hw.memsize`)를 추가했다. 직접 연결 서버는 "10코어 · 16 GB"로 표시하고, 칸 이름은 "CPU / 메모리"로 바꾼다.

### 테스트
- `SshMetricsServiceTest`: 데모 SSH로 샘플 수집, 1시간 지난 샘플 삭제, 설정 없으면 수집 안 함, Linux·macOS 한 번 읽기 출력 해석.
- `IpPrivacyTest`: 사설 IP와 호스트 이름 가리기, 긴 이름 우선, 드러내기.
- `MacHostStatsTest`: 이 Mac에서 실제 `ONE_SHOT`과 코어 수·메모리 읽기.

### 지원 범위
- Linux와 macOS 서버. Windows 서버(OpenSSH)는 터미널은 되지만, 모니터링·서버 정보·Docker 명령이 PowerShell용으로 따로 필요해서 아직 지원하지 않는다.

## 2026-09-28 · 직접 연결 서버 2단계: macOS 호스트

맥미니 같은 macOS 컴퓨터에는 `/proc`가 없어서, 실시간 모드와 서버 정보가 리눅스 명령으로는 비어 나왔다. 원격 명령이 `uname`을 보고 macOS면 같은 형식의 출력을 macOS 도구로 만들어 낸다. 그래서 Java 파서는 거의 그대로다.

| 항목 | Linux | macOS |
|---|---|---|
| CPU | `/proc/stat` 누적 카운터의 차이 | `iostat -n0 -c 2 -w 1`의 마지막 줄 us+sy를 `@cpu <퍼센트>` 줄로 (1초 걸리므로 루프는 1초 더 쉰다) |
| 메모리 | MemTotal / MemAvailable | `hw.memsize`, `vm_stat`의 free + inactive + speculative + purgeable 페이지 × 페이지 크기 |
| 네트워크 | `/proc/net/dev` | `netstat -ibn`의 `<Link#>` 줄을 `/proc/net/dev` 모양으로 바꿔 출력(lo 제외, 주소 칸이 빈 인터페이스도 처리) |
| 업타임 | `/proc/uptime` | 현재 시각 − `kern.boottime`의 `sec` |
| OS | `/etc/os-release` | `macOS <sw_vers -productVersion>` |
| 디스크 | `df -Pk /` | `df -Pk /System/Volumes/Data` (`/`는 작은 봉인된 시스템 볼륨이다) |
| 열린 포트 | `ss -tln` | `netstat -an -p tcp`. BSD 형식(`*.22`, `127.0.0.1.631`)도 파서가 읽는다 |

- **Docker:** 비대화형 SSH의 macOS PATH에는 `/usr/local/bin`(Docker Desktop)과 `/opt/homebrew/bin`이 없다. 그래서 Docker 명령 앞에 PATH를 덧붙인다(리눅스에는 영향 없음).
- **셸:** macOS의 로그인 셸은 zsh다. 명령은 POSIX sh와 zsh 양쪽에서 돈다.
- **버그 수정(개발 중):** `kern.boottime` 출력의 `usec = …`까지 `sec =`로 잡혀서 업타임이 틀리게 나왔다. 줄 맨 앞의 `{ sec =`만 읽도록 고쳤다.
- **테스트:** `MacHostStatsTest`는 macOS에서 실제 명령을 `/bin/zsh`로 실행하고 해석한다(업타임, macOS 버전, 디스크, 스냅샷 2개 → CPU·메모리 %). CI의 macOS 실행기에서도 돈다. `@cpu` 줄 해석과 BSD netstat 줄 해석은 모든 OS에서 테스트한다.

## 2026-09-28 · 컨테이너 셸 · DB 콘솔

컨테이너 목록에서 컨테이너를 고르고 **셸**을 누르면, 새 터미널 탭에서 그 컨테이너 안의 셸이 열린다. MySQL·MariaDB·PostgreSQL·Redis·MongoDB 이미지면 **MySQL 콘솔** 같은 버튼이 하나 더 나오고, 누르면 DB 클라이언트가 바로 열린다. 탭 제목은 `서버 › 컨테이너 (MySQL)`.

- **동작:** SSH exec 채널에 PTY를 붙여 `docker exec -it <id> sh -c '…'`를 실행한다(`ShellConnector.open(..., command)`). 로그인 셸 대신 이 명령이 탭의 세션이 되어서, `exit`하면 탭이 "종료됐어요"가 된다. 창 크기 변경도 그대로 전달된다.
- **셸:** 컨테이너에 bash가 있으면 bash, 없으면 sh(alpine 등).
- **DB 콘솔:** 이미지 이름의 마지막 부분(태그·다이제스트 제외)으로 고른다.

  | 콘솔 | 이미지 이름 | 실행 |
  |---|---|---|
  | MySQL | mysql / mariadb / percona | `mariadb`나 `mysql`, `-u root -p` |
  | PostgreSQL | postgres / postgis / timescale | `psql -U "${POSTGRES_USER:-postgres}"` |
  | Redis | redis / valkey / keydb | `redis-cli` |
  | MongoDB | mongo | `mongosh`, 없으면 `mongo` |

  - exporter, express, commander, insight, admin, operator, proxy, backup, router가 들어간 이미지는 DB 본체가 아니므로 제외한다.
  - 비밀번호는 저장하지 않는다. 클라이언트가 터미널에서 물어본다.
- **보안:** 컨테이너 id는 기존처럼 16진수인지 검사한다. `sh -c` 안의 스크립트는 코드에 고정된 상수라, 서버에서 받은 이름이나 문자열은 셸에 들어가지 않는다. 작은따옴표로 감싸서 `$POSTGRES_USER`는 컨테이너 안에서 풀린다.
- **데모:** 데모 서버마다 `mysql:8.4` 컨테이너가 생겼다. 가짜 컨테이너 셸과 MySQL·PostgreSQL·Redis·Mongo 콘솔이 몇 가지 명령에 답한다(`DemoContainerShell`).
- **테스트:** 내장 MINA 서버로 PTY 명령에 `TERM=xterm-256color`가 붙고 일괄 실행(exec)에는 붙지 않는 것을 확인한다. 명령 문자열, 이미지 판별(exporter·관리 UI 제외), id 주입 거부도 확인한다. 스냅샷 `terminal-mysql.png`로 화면을 확인했다.

- **디스코드 알림은 "준비 중":** 실제 채널로 시험하기 전까지 사용자에게 열지 않기로 했다(사용자 결정).
  - `AlertService.AVAILABLE = false` 하나로 막는다. 설정 창에는 "디스코드 알림 · 준비 중"과 설명만 보이고, 테스트 버튼과 입력칸은 숨긴다. 저장할 때도 알림 설정은 검사하거나 저장하지 않는다.
  - `MainFrame`은 감시 이벤트(onInventory/onCpu)를 넘기지 않는다. 코드와 테스트는 그대로 두어서, 값만 바꾸면 다시 열린다.
- **보관 CI 수정:**
  - 빌드 9에서 "이전 빌드 보관" 단계가 실패했다. gh는 초안(draft) 릴리스에 파일을 올린 뒤 공개하는데, 중간에 실패해서 초안 `beta-8`이 남은 것으로 보인다. 로그는 로그인해야 볼 수 있어서 확정은 못 했다.
  - 빌드 10은 그 초안을 "이미 보관됨"으로 보고 건너뛰었고, 그사이 `beta`가 빌드 10으로 바뀌어 **빌드 8 파일은 공개 보관되지 못했다**. 보관은 `beta-10`부터 시작한다.
  - 고친 것: 보관 단계의 오류를 annotation으로도 남긴다(로그인 없이 API로 볼 수 있다). `isDraft`를 확인해 초안이 남아 있으면 지우고 다시 만든다. 태그 커밋은 `git rev-list -n 1 beta`로 찾는다. `download-artifact`를 v5로 올렸다(Node 20 경고).
  - 초안 `beta-8`이 남아 있다면 저장소 소유자만 볼 수 있다. Releases 페이지에서 지워도 된다.

## 2026-09-28 · 빌드별 보관 릴리스

앱 안 업데이트가 실제 환경에서 확인됐다. macOS에서 빌드 7 → 8로 앱이 스스로 받고, 점검하고, 교체한 뒤 다시 열렸다. `xattr` 명령은 필요 없었다.

사용자 요청: 설치 파일을 최신 하나로 덮어쓰지 말고 빌드마다 남기기(전부 보관). 베타가 끝나면 한꺼번에 지울 수 있게.

| 릴리스 | 역할 |
|---|---|
| `beta` | 매번 교체되는 "최신" 표지판. 설치된 앱(빌드 7, 8)이 업데이트를 확인하는 곳이고 README 다운로드 링크도 여기를 가리켜서 없애면 안 된다 |
| `beta-<번호>` | 빌드마다 하나씩 영구 보관. 노트에 직전 보관 빌드 이후의 커밋 목록이 들어간다 |

- (계획) 보관은 빌드 8부터 시작한다. 실제로는 빌드 10부터 보관됐다(바로 위 항목 참고). CI는 `beta`를 덮어쓰기 전에, 지금 `beta`에 있는 빌드에 `beta-N`이 없으면 그 파일과 노트를 먼저 `beta-N`으로 옮긴다. 그래서 빌드 8이 다음 실행 때 자동으로 보관된다. 1~7은 이미 덮어써져서 없다.
- 한꺼번에 지우기: Actions → **delete beta archives** → Run workflow. 확인란에 `DELETE`를 입력해야 실행된다. `keep_from`에 번호를 넣으면 그 번호 이상은 남긴다. `beta` 표지판은 옵션을 켜야만 지운다(지우면 설치된 앱이 업데이트를 못 찾는다).
- 공개 저장소의 릴리스 파일은 파일당 2GB 제한만 있고 전체 용량 제한은 없다. 빌드당 약 230MB.

## 2026-09-28 · 앱 안에서 업데이트 설치

지금까지는 새 빌드 알림을 누르면 브라우저로 dmg를 받았고, macOS가 격리 표시(quarantine)를 붙여서 매번 `xattr` 명령을 쳐야 했다. 격리 표시는 브라우저처럼 스스로 붙이겠다고 설정한 앱만 붙이므로, 앱이 직접 받으면 이 단계가 필요 없다.

### 흐름
1. 트레이/메뉴 막대 → **새 베타 빌드 N 설치…** (또는 설정 → 업데이트 확인) → 확인 창
2. `UpdateInstaller.prepare`
   - 릴리스의 `SHA256SUMS.txt`를 먼저 받는다.
   - 업데이트 zip을 받으면서 SHA-256을 계산하고 진행률을 보여 준다(취소 가능).
   - 해시가 다르면 버린다.
   - 앱 바로 옆 `.infradesk-update/`에 푼다. macOS는 `ditto`로 풀어 심볼릭 링크·실행 권한·서명을 유지하고, Windows는 Java unzip에 zip slip 검사를 한다.
   - 새 앱의 `--self-test`가 통과해야 다음으로 넘어간다.
3. `startSwap`이 스크립트를 띄우고 앱이 종료된다.
4. 스크립트(`update-swap.sh` / `update-swap.ps1`)
   - 앱 프로세스가 끝날 때까지 기다린다.
   - 기존 앱을 `.previous`로 옮기고 새 앱을 그 자리로 옮긴 뒤 백업을 지운다. 새 앱을 옮기지 못하면 원래 앱을 되돌린다.
   - 앱을 다시 실행한다.
   - 기록은 로그 폴더의 `update.log`에 남는다.

### 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| macOS 업데이트 파일 | dmg와 별도로 `.app`을 `ditto`로 압축한 `InfraDesk-beta-macOS.zip` | dmg는 `hdiutil`로 마운트해야 하고 실패할 경우가 많다. zip은 풀기만 하면 된다. dmg는 첫 설치용으로 남긴다 |
| 무결성 | CI가 `SHA256SUMS.txt`를 올리고 앱이 대조 | 정식 코드 서명이 없어서, 적어도 전송 중 손상이나 다른 파일로 바뀐 것은 막는다(HTTPS + GitHub 릴리스) |
| 풀 위치 | 설치된 앱 바로 옆(같은 볼륨) | 교체가 이름 바꾸기 한 번이라 빠르고 원자적이다. Windows에서는 다른 드라이브로 폴더를 옮길 수 없다(`Move-Item`) |
| 교체 전 점검 | 새 앱의 `--self-test` | 깨진 빌드가 동작하는 앱을 덮어쓰지 않게 한다 |
| 설치할 수 없을 때 | 이유를 보여 주고 다운로드 페이지 열기로 대신 | Gradle로 실행 중, dmg 안이나 App Translocation 위치, 폴더 쓰기 권한 없음, 업데이트 파일이 없는 예전 릴리스 |
| 다운로드 클라이언트 | 리디렉트를 따라가는 별도 HttpClient | GitHub 자산 주소는 CDN으로 302 리디렉트된다. 기본 HttpClient는 리디렉트를 따라가지 않는다 |

### 테스트
- `UpdateInstallerTest`는 로컬 HTTP 서버(302 리디렉트 포함)로 확인한다: 해시 불일치 거부, 취소, zip slip 거부, 설치 가능 여부 판단, Windows 폴더 구조.
- macOS에서는 가짜 `.app`을 `ditto`로 압축해 받고, 자가 점검을 거쳐 `update-swap.sh`로 실제로 교체하는 과정까지 돈다. 자가 점검에 실패하는 빌드는 설치되지 않는 것도 확인한다.
- Windows 교체 테스트(`powershell`)는 CI의 Windows에서 돈다.
- 실제 패키징한 앱을 `ditto`로 압축했다 풀어도 격리 표시가 없고, `codesign -v`와 `--self-test`가 통과했다.

### 실제 환경
- 빌드 7: 릴리스에 `InfraDesk-beta-macOS.zip`과 `SHA256SUMS.txt`가 올라갔고, CI Windows에서 교체 스크립트 테스트가 통과했다. 사용자가 dmg로 마지막 수동 설치를 했다(`/Applications`).
- 빌드 8: 빌드 7에서 앱 안 업데이트를 처음으로 실제로 시험한다.

### 남은 일
- 임시(ad-hoc) 서명은 빌드마다 달라서, 업데이트 뒤 키체인이 "항상 허용"을 한 번 다시 묻는다. CI에 고정된 자체 서명 인증서를 넣으면 해결된다.

## 2026-09-28 · Windows 트레이 메뉴와 작업 관리자의 "???"

Windows에서 오른쪽 아래 트레이 메뉴와 작업 관리자의 앱 이름이 "??? ???"로 표시됐다.

- **트레이 메뉴:** AWT 네이티브 메뉴(`PopupMenu`)는 Windows에서 논리 폰트와 문자 집합 변환을 거쳐 그린다. 시스템 로캘 설정에 따라 한글이 "???"가 되고, 이모지(🟢)는 어떤 경우에도 그리지 못한다. 그래서 메뉴를 `TrayController.Entry` 목록(Label / Item / Separator / ServerMenu)으로 한 번만 만들고, 그리는 쪽을 플랫폼마다 나눴다.
  - macOS: 기존처럼 네이티브 메뉴를 쓴다. 메뉴 막대 메뉴는 네이티브여야 자연스럽고, 한글·이모지도 잘 나온다.
  - Windows: `SwingTrayMenu`가 FlatLaf `JPopupMenu`로 그린다. 상태는 이모지 대신 `StatusDot` 아이콘과 글자로 표시한다. 팝업에는 부모 창이 필요해서 커서 위치에 1px 투명 다이얼로그를 띄우고, 그 다이얼로그가 포커스를 잃으면(다른 곳을 클릭하면) 메뉴를 닫는다.
  - Windows 관례에 맞춰 왼쪽 클릭은 앱 열기, 오른쪽 클릭은 메뉴로 했다.
- **트레이 아이콘 색:** 템플릿 이미지는 macOS에만 있는 기능이라, Windows에서는 검은 아이콘이 어두운 작업 표시줄에 묻힌다. 레지스트리 `SystemUsesLightTheme`를 읽어 흰색이나 어두운색으로 그리고, 크기는 16·20·24·32px로 준비했다(배율 100~200%).
- **작업 관리자:** 작업 관리자는 exe의 파일 설명(FileDescription)을 앱 이름으로 보여 준다. jpackage `--description`에 넣은 한글 문장이 "???"로 기록돼서, ASCII `InfraDesk`로 바꿨다.
- `./gradlew snapshot`이 `tray-menu-windows.png`(메인 메뉴 + 서버 하위 메뉴)도 그린다. macOS에서 렌더링한 결과라 실제 Windows에서 위치와 포커스 동작은 사용자 확인이 필요하다.
- **실제 환경(Windows):** 트레이 메뉴 한글과 작업 관리자 이름("InfraDesk")이 제대로 나온다(사용자 확인, 2026-09-29).

## 2026-09-28 · 메모리 줄이기

Windows에서 실제 실행과 서버 추가가 확인됐지만, 작업 관리자에 약 500MB가 표시됐다. macOS에서 데모 모드를 같은 방식으로 재 보니(`footprint`, NMT) 기본 설정일 때도 약 480MB였다.

### 어디에 쓰였나 (macOS, 데모, 실행 25초 뒤)
| 항목 | 기본값 | 조정 후 |
|---|---|---|
| JVM 전체 (NMT committed) | 236MB | 77MB |
| └ Java 힙 | 112MB (실제 사용 약 20MB) | 약 17MB |
| └ G1 GC 자료구조 | 55MB | 0MB (SerialGC) |
| 그래픽 (창 버퍼·Metal 텍스처) | 48~224MB | 같음 |
| 나머지 네이티브 (AWT, 폰트, 라이브러리 malloc) | 약 150MB | 같음 |

- 살아 있는 객체는 약 20MB뿐이다. 하지만 JVM 기본값(G1, 초기 힙 = RAM의 1/64, 최대 = 1/4)은 힙을 크게 잡아 두고 잘 돌려주지 않는다. RAM이 큰 Windows PC일수록 초기 힙과 young 영역이 커져서 작업 집합이 수백 MB까지 불어난다.
- OCI SDK는 첫 계정에서 힙 약 16MB와 클래스/코드 약 30MB를 한 번 쓰고, 이후 계정마다 1MB가 채 안 늘어난다(오프라인 측정, 계정 3개).
- 그래픽 메모리는 창이 보이는지 가려졌는지에 따라 48MB와 224MB 사이를 오간다. macOS 창 서버의 몫이라 JVM 옵션으로는 줄지 않는다. `swing.volatileImageBufferEnabled=false`는 macOS에서 31MB를 줄이지만, Windows에서는 VRAM에 있던 버퍼를 프로세스 메모리로 옮기는 셈이라 쓰지 않았다.

### 결정
| 옵션 | 이유 |
|---|---|
| `-XX:+UseSerialGC` | 힙이 작은 데스크톱 앱이다. G1의 영역별 자료구조(약 55MB)가 필요 없고, 멈춤 시간도 수 ms 수준이다 |
| `-Xms16m -Xmx256m` | 필요할 때만 커진다. 상한은 실측(데모 약 20MB, OCI 3계정 약 40MB)에 터미널 스크롤백(탭당 5000줄)과 일괄 실행 출력(최대 256KB)을 더해도 여유 있게 잡았다 |
| `-XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=30` | GC 뒤에 남는 빈 힙을 OS에 돌려준다 |
| `-XX:TieredStopAtLevel=1` | C1 JIT만 쓴다. 이 앱은 I/O 대기 위주라 C2 최적화가 필요 없고, 컴파일러 메모리와 코드 캐시가 약 10MB 준다 |

- `build.gradle.kts`의 `appJvmArgs` 목록 하나를 `run`, `runDemo`, `installDist` 실행 스크립트, jpackage `--java-options`가 함께 쓴다.
- 결과: 패키징된 앱(데모)의 footprint가 약 480MB에서 약 410MB(창이 보일 때)로, 그래픽을 뺀 나머지는 약 250MB에서 약 180MB로 줄었다. Windows에서는 기본 힙이 RAM에 비례해 컸던 만큼 효과가 더 클 것으로 보고, 사용자 측정을 기다린다.
- **실제 환경(Windows, 빌드 14):** 작업 관리자 기준 약 500MB에서 약 200MB로 줄어 안정됐다(사용자 확인, 2026-09-29).
- 참고로 JVM 기본값에서 옵션을 바꿔가며 잰 수치(데모, 25초): 기본 G1은 JVM 236MB, G1+`-Xmx192m`+주기적 GC는 141MB, SerialGC+`-Xmx160m`은 86MB, 여기에 C1 전용을 더하면 77MB.

## 2026-09-28 · Docker 컨테이너

- 사용자 질문 "도커 같은 건 못 가져오겠지?" → SSH로 가능 (CLAUDE.md 확장 계획, Docker TCP 2375는 절대 쓰지 않음).

## 2026-09-28 · 로그 · 앱 정보/업데이트 · 로그인 시 실행

사용자가 고른 세 가지. 테스트는 `./gradlew run`으로.

### 로그 파일 + 오류 처리
- `app.Logging`: java.util.logging → `~/Library/Logs/InfraDesk/infradesk-N.log`(macOS, 콘솔 앱에서도 보임) / `%LOCALAPPDATA%\InfraDesk\logs`(Windows), 2 MB × 5개 순환, 콘솔에도 출력. 우리 코드는 INFO, 라이브러리는 WARNING 이상.
- `slf4j-nop` → `slf4j-jdk14`: 버려지던 OCI SDK·MINA SSHD 경고도 같은 로그로.
- **모든 줄을 가림 처리** (`Logging.redact`): 개인키(PEM, 잘린 것 포함), 디스코드 웹훅 URL, 공인 IPv4(`x.x.x.24`), OCID(`ocid1.instance.oc1.<region>.…123456`). 로그를 이슈에 붙여도 되게.
- `ui.ErrorReporter`: 처리되지 않은 예외(EDT 포함)를 스택과 함께 기록하고 30초에 한 번까지 토스트("설정 → 앱 정보 → 로그 폴더 열기").
- 기록하는 일: 시작(빌드·Java·OS·데모/최소화), 서버 제어 요청·결과, SSH 연결 성공·실패, 업데이트 확인, 자동 실행 변경, 종료.
- 실사용 로그 확인: 시작·업데이트 확인 기록 정상, 개인 정보 없음. 잡음이던 OCI SDK 안내 3줄(VPN 장비 설정 API의 스트림 안내, OCI 인스턴스 안에서만 의미 있는 IMDS 안내)은 해당 로거만 SEVERE로 낮춰 숨김. 이름 없는 가상 스레드는 `[virtual-<id>]`로 표시.

### 앱 정보 + 업데이트 확인
- Gradle `generateBuildInfo` → `build-info.properties`(version, build, commit). CI는 `-PbuildNumber=<run>` `-Pcommit=<sha>`, 로컬은 `build=dev` + git HEAD.
- 표시: "1.0.0 Beta (빌드 12 · f4102ce)" / "1.0.0 개발 빌드 (f4102ce)" — 설정 → 앱 정보, 메뉴 막대 메뉴 아래쪽.

## 2026-09-28 · 키체인 암호를 계속 묻는 문제 → 암호화 금고

### 문제
- 설치한 앱에서 "항상 허용"을 눌러도 **버튼마다 macOS 로그인 암호를 물음**.
- 원인 1: 비밀값마다 키체인 항목이 따로 있었고(API 키 2, SSH 키 여러 개, 웹훅), "항상 허용"은 **항목마다** 적용됨. 게다가 SSH 버튼·서버 선택·실시간 토글마다 `isConfigured`가 키체인을 읽었음.
- 원인 2: jpackage 앱은 **ad-hoc 서명**(`codesign`: `Signature=adhoc`)이라 macOS가 "항상 허용"을 안정적으로 기억하지 못함.

### 조치
- `storage.VaultSecretStore`: 모든 비밀값을 **AES-256-GCM 암호화 파일** `secrets.vault` 하나에 저장(JSON 맵 전체 암호화 → 이름도 안 보임, 12바이트 IV, 128비트 태그, 매직 헤더를 AAD로). 키체인에는 **무작위 256비트 마스터 키 하나**만.
- 키체인은 **실행당 최대 한 번** 읽고, 복호화한 값은 메모리에 유지.
- 기존 키체인 항목은 필요할 때 한 번 읽어 금고로 옮김(없는 이름도 한 번만 확인).
- 마스터 키가 없는데 금고 파일이 있으면 새 키를 만들지 않고 오류 (데이터 덮어쓰기 방지). 키가 틀리면 GCM 인증 실패로 오류.
- CLAUDE.md의 "AES-GCM 암호화" 방향과 일치. 파일 권한 `rw-------`.
- 테스트 115개 통과 (왕복, 키체인 1회 읽기, 암호화·권한, 잘못된 키, 이전).

### 2차: 이전할 때도 항목마다 물음 → 일괄 이전 명령
- 금고로 바꾼 뒤에도 옛 키체인 항목을 **처음 쓸 때마다** 하나씩 옮기느라, 설치한 앱이 서버마다 한 번씩 암호를 물음.
- `--migrate-secrets`: 계정·SSH 설정·웹훅에서 이름을 모아 옛 항목을 금고로 옮기고 **옛 항목 삭제**, 금고에 "이전 완료" 표시 → 이후 설치한 앱은 옛 저장소를 **전혀 조회하지 않음**.
- 옛 항목을 만든 JVM(`./gradlew run`)에서 실행하면 항목을 만든 프로그램이 읽는 것이라 macOS가 묻지 않음. 마스터 키를 설치한 앱이 만들었다면 그 한 항목만 한 번 물음.

### 남은 것
- ad-hoc 서명이라 **앱을 다시 빌드할 때마다** macOS가 마스터 키 접근을 한 번 더 물을 수 있음. 해결책: 로컬 자체 서명 인증서로 `jpackage --mac-sign` (서명 신원이 고정되어 "항상 허용"이 유지됨).
- 옛 키체인 항목은 지우지 않음(지울 때도 암호를 물을 수 있어서). 키체인 접근 앱에서 "InfraDesk" 항목 중 `vault.masterKey` 외에는 지워도 됨.

### 한글 입력기에서 붙여넣기가 안 되고, 우클릭 붙여넣기 후 입력이 멈춤
- `--debug-input` 기록: 입력기 `ko_KR`에서 ⌘V를 누르면 **⌘ 누름만 Java에 오고 V는 오지 않음**. 한글 입력기가 ⌘V를 가져가서 입력칸의 단축키가 실행되지 않음.
- 우클릭 → 붙여넣기 후에는 클릭·키 입력이 **창에 전달되지 않음**. 그때 `jstack`(Java EDT)과 `sample`(macOS 메인 스레드)을 떠 보니 둘 다 교착 없이 다음 이벤트를 기다리는 중 → 입력이 창까지 안 옴. 전역 마우스 리스너에서 이벤트를 가로채 메뉴를 직접 띄우던 방식이 macOS 모달 대화 상자와 맞지 않은 것으로 판단.
- 조치:
  1. 영문만 들어가는 칸(OCID, fingerprint, SSH 포트, 웹훅 URL)은 `enableInputMethods(false)` → 입력기를 거치지 않으므로 ⌘V가 바로 도착해야 함. 한글 오입력도 막음.
  2. 우클릭 메뉴를 표준 `setComponentPopupMenu`로 교체 (입력칸이 추가될 때 붙임). 직접 띄우기·이벤트 소비 제거.
  3. macOS 메뉴 막대에 "편집" 메뉴(잘라내기·복사·붙여넣기·모두 선택). 입력칸과 터미널 모두에 동작. 대화 상자가 떠 있을 때도 보이도록 기본 메뉴 막대로도 등록.
- 2차 확인 (`--debug-input`): 입력기를 끈 OCID 칸에서는 이제 ⌘Z, ⇧⌘← 같은 단축키가 도착함 → 입력기 문제는 해결된 것으로 보임.
- 그런데 표준 우클릭 메뉴로 바꿔도 **메뉴를 여는 순간** 또 입력이 멈춤 (`MOUSE_PRESS popup=true` → `FOCUS_GAINED JRootPane` → 이후 입력 없음).
  - 원인: FlatLaf `FlatPopupFactory`는 macOS에서 `Popup.dropShadowPainted`가 켜져 있으면 **모든 팝업을 네이티브 창(heavyweight)으로 강제**함 (그림자·둥근 테두리용). 모달 대화 상자 위의 이 창이 입력을 잡고 놓지 않음.
  - 조치: `Popup.dropShadowPainted=false` → Swing 기본 규칙으로 창 안에 들어가면 창 내부(lightweight)에 그림. 같은 대화 상자의 리전 선택 상자 등 모든 팝업에 적용.
  - 입력칸 우클릭 메뉴는 한때 제거했다가, 사용자가 필요로 해서 **다시 추가**. 원인(네이티브 팝업 창)을 끈 상태에서, 팝업이 창 밖으로 나가면 Swing이 여전히 네이티브 창을 쓰므로 메뉴 위치를 항상 창 안으로 조정. 확인: 입력칸 왼쪽·오른쪽 끝을 눌러도 팝업이 같은 대화 상자 안(lightweight)에 그려짐.
- 사용자가 ⌘Z를 눌렀는데 Swing 입력칸엔 실행 취소가 없음 → `components.TextUndo`: 모든 입력칸에 실행 취소/다시 실행(⌘Z, ⇧⌘Z), 편집 메뉴에도 추가.

### 공인 IP 가리기
- 사용자 제안: 공인 IP는 중요하니 버튼을 눌렀을 때만 보이게.
- `ui.IpPrivacy`: 앱 전체 상태, **켤 때마다 가린 상태로 시작**. 공인 IPv4는 `•••.•••.•••.104`(마지막 자리만)로 표시. 사설·예약 대역(10/8, 172.16/12, 192.168/16, 127/8, 100.64/10)은 그대로.
- 서버 상세 공인 IP 칸: 👁 보기/숨기기, 복사(가려져 있어도 실제 IP 복사).
- 같이 가려지는 곳: 터미널 상태바 주소, 연결 실패 안내, 정지·재부팅 확인 창, 호스트 키 확인 창, 모니터링 상태 줄, SFTP 오류, 일괄 실행 결과 오류. 보이기로 바꾸면 모두 즉시 갱신.
- 한계: 터미널 **안에** 서버가 출력하는 글자(예: `Last login … from <IP>`)는 가리지 않음.
- 테스트 104개 통과.

### 서버 정보 칸 채우기 (업타임 · OS · 부트 볼륨 · 열린 포트)
- 사용자 질문: "OCPU·메모리·IP·생성일밖에 안 보이는데 다른 건 못 가져와?" → 나머지 4칸은 서버 안에서 봐야 정확한 값이라 SSH로 한 번 읽음.
- `ssh.HostFacts`: POSIX sh 명령 하나로 `/proc/uptime`, `/etc/os-release`(없으면 `uname -sr`), `df -Pk /`, `ss -tln`(없으면 `netstat -tln`)을 섹션별로 출력하고 파싱. 포트는 localhost(127.x, ::1, `%lo`) 전용을 뺀 LISTEN 포트.
- 서버를 선택할 때 SSH 설정이 있으면 백그라운드로 읽고 **5분 캐시**. SSH 설정 저장 직후·서버가 다시 실행될 때 새로 읽음. 설정이 없으면 "SSH 설정 후 표시", 실패하면 "SSH로 읽지 못함".
- 표시: 업타임 "14일 6시간", 부트 볼륨 "사용 / 전체 GB"(툴팁에 %), 포트 4개까지 + "외 N개"(툴팁에 전체).
- 데모: 서버마다 다른 가짜 값.
- 테스트 101개 통과 (`ss`/`netstat` 형식, 빈 섹션, 데모 응답, 표시 형식).

### 대화 상자 문구 잘림
- 두 번째 계정(서버 second-server)을 추가하며 확인: `~/.ssh/config` 자동 채우기 동작, 하지만 안내 문구가 창 밖으로 잘림.
- 원인: JLabel에 HTML `width`를 줬는데 macOS에서 실제보다 넓게 계산됨. JTextArea 단어 줄바꿈은 한글 단어 중간("서/버")에서 끊음.
- `components.WrappingLabel`: 폭을 고정하고 **띄어쓰기에서만** 줄바꿈을 직접 계산 (한 단어가 줄보다 길면 글자 단위). SSH 설정·계정 추가·설정 창의 상태/안내 문구에 적용 → 긴 오류 메시지도 잘리지 않음.

### `~/.ssh/config`에서 SSH 설정 가져오기
- 사용자가 이미 `~/.ssh/config`에 서버별 Host(HostName·User·IdentityFile)를 정리해 두고 있어서, SSH 설정 창을 처음 열 때 **서버 공인 IP와 HostName이 같은 Host**를 찾아 사용자 이름·포트·키 파일을 미리 채움. 없으면 서버 이름과 같은 Host 별칭으로 찾음.
- `ssh.SshConfig`: OpenSSH처럼 블록을 순서대로 보며 **먼저 나온 값이 우선**, `Host *` 기본값, `*`/`?` 와일드카드, `!` 제외, `Key=Value`·따옴표·주석, IdentityFile의 `~`와 `%d %u %h %n %r %%` 확장, 여러 IdentityFile 중 실제로 있는 첫 파일. `Match`·`Include`는 무시.
- 키는 창에 미리 읽어 두기만 하고, **저장을 눌러야** 키체인에 들어감. 창에 "~/.ssh/config의 'my-server'에서 가져왔어요 (키: …)" 안내.
- 데모 모드에서는 실제 설정 파일을 읽지 않음.
- 실제 설정으로 확인: my-server(203.0.113.104) → `my-server`, `ubuntu`, 22, `my-server.key`. 키 내용은 읽지 않고 파일 이름만 확인.
- 테스트 91개 통과 (SSH config 6개 추가).
- 과정에서 나온 문제: 붙여넣기가 안 됨 → 우클릭 메뉴 추가, `--debug-input` 진단 모드 추가. 재실행 후 정상 (원인 기록은 못 남김).

## 2026-09-28 · 6단계: 편의 기능

### 6-1. 저장된 명령어 · 일괄 실행
- 터미널 화면 오른쪽 패널 (목업 `terminal.html`): 저장된 명령어 카드, 일괄 실행, 맨 아래 [SFTP 파일].
- **저장된 명령어**: 클릭하면 선택된 터미널 탭에 입력 후 실행. [+]로 추가, 우클릭으로 편집·삭제(삭제는 확인). `commands.json`에 저장 (비밀값 아님). 연결된 탭이 없으면 안내.
- **일괄 실행**: 실행 중 서버만 선택 가능 (정지된 서버는 "(정지됨)"으로 비활성). 실행 전에 명령어와 대상 서버를 보여주고 확인. 서버마다 PTY 없는 exec 채널로 병렬 실행, 60초 제한, 출력 256KB까지.
- **결과 창**: 서버별 성공/실패/종료 코드(색 점 + 글자), 선택한 서버의 출력. 결과가 도착하는 대로 갱신.
- 데모: 목업의 명령어 4개가 미리 저장돼 있고, 가짜 셸이 `docker restart/logs`, `apt`, `du`에도 응답.
- 테스트 64개 통과 (실행 결과·종료 코드, 연결 실패, 시간 초과, 명령어 저장).

| 결정 | 이유 |
|---|---|
| 저장된 명령어는 클릭 즉시 실행 (Enter 포함) | 목업의 "명령어 버튼" 용도. 사용자가 직접 저장한 명령어만 들어감 |
| 일괄 실행은 항상 확인 창 | 여러 서버에 동시에 영향을 주는 작업 |
| 명령어는 전체 공용 (서버별 아님) | 목업 구조. 필요해지면 서버 태그로 확장 |

### 6-2. SFTP 파일
- 오른쪽 패널 [SFTP 파일]: 선택된 탭의 서버로 열림 (탭이 없으면 실행 중 서버 메뉴). SSH 설정이 없으면 설정 창부터.
- 파일 탐색기 창 (여러 개 동시에 열 수 있음): 경로 입력·상위 폴더·새로고침, 폴더 먼저 정렬, 두 번 클릭(또는 Enter)으로 폴더 이동/파일 다운로드, 업로드·다운로드 진행률, 삭제(확인, 폴더는 비어 있어야 함). 덮어쓰기는 로컬·원격 모두 확인.
- `ssh.RemoteFiles` 인터페이스 + MINA SFTP 구현(`sshd-sftp`), 데모는 메모리 파일 트리(업로드도 메모리에 남음).
- 원격 이름을 로컬 파일 이름으로 쓸 때 `/ \ :`와 `..`를 치환 (`RemoteFiles.safeLocalName`).
- 테스트: **테스트 안에서 SFTP 서버를 띄워** 목록, 200KB 업로드·다운로드, 삭제 확인. 경로 도우미, 데모 트리.

### 6-3. 디스코드 웹훅 알림
- 사이드바 ⚙ → **설정 창**: 알림 사용, 웹훅 URL(키체인 저장, 입력칸은 가려짐), 알림 종류, CPU 기준(기본 90% · 5분), [테스트 메시지 보내기].
- **알림 종류** (`alert/AlertMonitor`, 문제마다 한 번 + 복구 알림 한 번):
  - 🔴 실행 중이던 서버가 정지·삭제로 바뀜 → 🟢 다시 실행 중. 앱에서 정지·재부팅한 서버는 15분 동안 제외.
  - ⚠️ 계정 연결 오류 → ✅ 복구.
  - 🔥 CPU가 기준 이상으로 N번(1분마다) 연속 → ✅ 정상. 중간에 한 번이라도 내려가면 다시 셈.
  - 앱을 켰을 때 이미 멈춰 있던 서버는 알리지 않음.

## 2026-09-28 · 2단계: 계정·서버 목록

### 한 일
- **데모 모드** (`./gradlew runDemo`, 또는 `--demo` 인자): 가짜 계정 3개·서버 5대 (계정 A는 한 계정에 서버 여러 대인 경우를 보여주려고 3대: discord-bot, api-gateway, batch-worker). 설정 파일·키체인·네트워크를 쓰지 않음. 타이틀바에 "데모 모드" 배지.
- **storage**: `JsonAccountStore`(계정 설정 JSON, 원자적 저장, POSIX에서 `rw-------`), `KeychainSecretStore`(OS 키체인), 데모·테스트용 인메모리 구현.
- **provider/oracle**: `OracleProvider` — 인스턴스 목록(페이지 처리), VNIC로 공인/사설 IP, 시작(START)/정지(SOFTSTOP)/재부팅(SOFTRESET) 호출, OCI 오류를 한국어 메시지로 변환. 메트릭은 5단계.
- **provider/demo**: `DemoProvider` — 지연 시간 흉내, 시작/정지/재부팅 시 8초간 전이 상태(정지 중 등)를 거쳐 안정.
- **service**: `ProviderRegistry`(ProviderType → 팩토리), `InventoryService`(계정 추가/삭제, 계정별 병렬 조회 — 한 계정 실패가 다른 계정에 영향 없음, 연결 테스트), `AccountValidation`.
- **UI**: 계정별 서버 목록(검색, 키보드 선택, 우클릭으로 계정 삭제), 서버 상세(헤더·상태 배지·4×2 정보 그리드), 계정 추가 다이얼로그(연결 테스트, 개인키 파일 선택), 새로고침.
- 네트워크 호출은 모두 `Async`(가상 스레드)에서 실행하고 결과만 EDT로 넘김.
- 스냅샷: `main.png`, `main-empty.png`, `add-account.png`.
- 테스트 19개 통과 (저장소, 서비스, 검증, 데모 전이, OCI 매핑).

### 결정한 것
| 항목 | 결정 | 이유 |
|---|---|---|
| 비밀값 저장 | API 개인키 **내용**을 OS 키체인에 저장 (`account.<id>.privateKey`) | 목업 문구는 "마스터 비밀번호 암호화"였지만 CLAUDE.md 우선순위(키체인 → 불가 시 AES-GCM)에 따름. 안내 문구도 키체인으로 수정 |
| 계정 설정 | `Account.properties`에 OCID·fingerprint (비밀 아님) | OCID는 커밋 금지 대상이지만 로컬 설정 파일은 괜찮음. 파일 권한은 소유자만 |
| 조회 범위 | 기본은 tenancy 루트 compartment. `compartmentOcid` 속성으로 바꿀 수 있음 | 계정당 서버 1대인 프리티어 구성에 맞춤 |
| IP 조회 | compartment의 VNIC 연결 목록을 한 번 조회 후 VNIC별 `getVnic` | 인스턴스마다 attachment를 조회하는 것보다 호출 수가 적음 |
| 정지/재부팅 | `SOFTSTOP`, `SOFTRESET` (OS에 종료 신호를 먼저 보냄) | 데이터 손상 위험이 적은 쪽 |
| `CloudProvider` | `AutoCloseable` 추가 (기본 no-op) | OCI SDK 클라이언트 해제 |
| 서비스 계층 | 새 패키지 `service/` | UI가 storage·provider를 직접 조립하지 않도록 |
| 로깅 | `slf4j-nop` | OCI SDK 로그가 콘솔에 쏟아지지 않게. 필요해지면 로거 연결 |
